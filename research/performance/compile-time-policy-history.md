# VeriQueue compile-time performance policy roadmap

## Decision

VeriQueue is not being rewritten. The public queue remains one API and one correctness model, while performance work is treated as an evidence-selected family of compile-time hot paths.

The cross-algorithm campaign merged in PR #28 established that the remaining deficit is regime-specific: different external queues win different cells. A universal hot path is therefore not assumed to be optimal.

## PR29: forensic policy laboratory

PR29 is deliberately benchmark-only. Production `include/veriqueue/spsc_queue.hpp` is not modified by the new policy candidates.

The forensic matrix measures the following candidate mechanisms in the same randomized rounds as the pinned external comparators:

- current production VeriQueue;
- existing single-owner cursor;
- existing cached-limit cursor;
- existing split-control and split+cached-limit controls;
- single-owner cached-limit with sequential raw-lifetime storage;
- single-owner cached-limit with the current global 16-byte stripe reproduced as an explicit control;
- single-owner cached-limit with a local tiled 16-byte stripe;
- typed, already-live trivial storage with ordinary assignment;
- representation-copy (`memcpy`) trivial storage;
- tiled variants of the two trivial-copy candidates.

All queue candidates retain relaxed owner reads, acquire peer observation, and release publication. The laboratory introduces no lock, CAS, RMW, fence, retry protocol, or runtime policy branch.

### Tiled 16-byte mapping

For a 16-slot / 256-byte tile, logical offsets are locally transposed:

```text
0 -> 0   1 -> 4   2 -> 8   3 -> 12
4 -> 1   5 -> 5   6 -> 9   7 -> 13
8 -> 2   9 -> 6  10 -> 10 11 -> 14
12 -> 3 13 -> 7  14 -> 11 15 -> 15
```

Adjacent logical 16-byte values therefore occupy different cache lines, while the active tile remains within 256 bytes instead of being scattered across the complete ring. The mapping is a permutation and does not alter capacity semantics.

### Trivial-copy experiments

The typed-storage candidate intentionally constrains itself to trivial, default-constructible benchmark payloads. The `memcpy` candidate stores only object representation bytes and is constrained to trivially copyable, trivially destructible payloads. These are code-generation probes, not yet public API specializations.

A production trivial-type specialization is allowed only after code-generation and performance evidence identifies a winner and the generic API constraints can be preserved without requiring default construction.

## Evidence generated by PR29

The `Forensic Policy Lab` workflow has two modes:

- pull-request mode: focused capacities 256 and 1024, all four benchmark payload sizes, x64/ARM64, GCC/Clang, lightweight repeated measurements;
- manual `full` mode: capacities 2, 64, 256, 1024 and 65536 with configurable transfers, warmups and repetitions.

Every measured round includes all policy candidates and all four pinned external implementations. Ordering is randomized by the existing comparator campaign runner, affinity and FIFO correctness fail closed, and the policy analyzer reports paired bootstrap confidence intervals both against production VeriQueue and against the fastest external implementation in each cell.

Representative 16/64/256-byte enqueue/dequeue assembly is also emitted for production VeriQueue, the main new policy candidates and all external comparators. The assembly analyzer records instruction, branch, address-generation, AArch64 load/store/acquire/release, `memcpy` reference and forbidden-synchronization indicators. Assembly is structural supporting evidence, not causal proof.

## Promotion sequence

### PR30 — tiled small-slot storage

Promote tiled storage only in architecture/compiler/type/capacity regimes where it beats both the current mapping and sequential control with a stable confidence interval and no material neighboring-cell regression.

### PR31 — cached-limit cursor policy

Promote cached-full-limit equality only in regimes where the forensic matrix proves a repeatable win. Do not infer a universal cursor policy from one architecture.

### PR32 — trivial-type fast storage

Select direct typed assignment, explicit representation copy, or the current lifetime path from measured code generation and throughput. Generic non-trivial object semantics remain unchanged.

### PR33 — x64/GCC code-generation recovery

Use the PR29 assembly evidence to isolate the remaining x64/GCC 64/256-byte pathologies. Structural changes require a demonstrated code-generation mechanism rather than a benchmark-only correlation.

### PR34 — policy synthesis

Encode only proven decisions with traits and `if constexpr`/compile-time constants. Runtime workload detection or benchmark-cell lookup is forbidden. The public API and correctness model remain singular.

### PR35 — dominance qualification

Re-run the complete external development matrix and an independent holdout matrix. The holdout must include capacities such as 4, 8, 16, 32, 128, 512, 2048, 4096 and 16384; payloads such as 24, 32, 48, 96 and 128 bytes; and alternative valid CPU placements where available.

## Acceptance gates

Production promotion requires all of the following:

1. correctness suites remain green, including unit, lifetime, wraparound, stress, sanitizers, fuzz, Relacy/model checks and mutation checks appropriate to the selected policy;
2. no weaker memory ordering is introduced for performance;
3. no loss of generic non-trivial object semantics;
4. no benchmark-specific runtime branch or globally relaxed compiler setting;
5. development matrix reaches zero statistically significant loss cells against the best external comparator, with every comparator geomean above parity and an overall lower 95% confidence bound above 1.0;
6. holdout qualification has no material regression cluster, no architecture/compiler lane below parity, and an overall lower 95% confidence bound above 1.0.

Until those gates are observed, the correct status is **credible path to comparative SOTA**, not comparative SOTA achieved.
